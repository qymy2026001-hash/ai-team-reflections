# 优先级与需求变更

**简体中文** | [English](en/priorities-and-scope.md)

状态：建议方案。适用于计划执行中经常新增需求、修复或跨团队依赖的团队。

## 问题分析

需求持续进入而原承诺不变，会增加任务切换和隐性排队。仅要求成员提高效率，无法解决容量不足和优先级冲突。优先级决策需要说明收益、紧迫性、实施成本及被替换的工作。

## 建议做法

1. 统一需求入口，记录目标、提出人、期限原因、验收条件和影响范围。
2. 产品负责人提出排序，研发提供工作量范围、依赖和风险判断。未知项较多时先安排限时调研。
3. 计划前预留评审、测试、维护与协作容量，依据历史负担调整，不设没有依据的固定比例。
4. 执行中新需求进入时，选择延期、替换、缩小范围或增加明确支持。同步记录旧承诺的变化。
5. 只有符合事先约定的紧急条件才走快速通道，例如正在发生的严重服务中断；紧急修复完成后补充原因与影响记录。

## 决策记录

| 字段 | 需要回答的问题 |
| --- | --- |
| 目标 | 这次调整解决什么问题？ |
| 紧迫性 | 为什么必须在当前周期完成？ |
| 成本与不确定性 | 大致占用多少容量，哪些条件尚不清楚？ |
| 取舍 | 哪项工作延期或缩小范围，由谁确认？ |
| 交付证据 | 什么结果代表本次调整完成？ |

## 成本与边界

过度细化评分容易制造虚假的精确度。对小任务可用简短讨论记录决定；对跨团队或高风险变更再补充详细分析。管理者需及时做出取舍，否则需求入口只会成为新的等待点。

## 如何验证

试行一个周期，记录计划内交付、临时插入、被替换任务及原因；观察未完成任务是否主要来自范围变化或其他阻塞。将交付结果与范围变化一起回顾，不用单一按期率评价个人。

下一步：选定一位优先级决策人，并仅用隐私政策允许的信息，把一次真实变更写入[实践记录](实践记录.md)。
