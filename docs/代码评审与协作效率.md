# 代码评审与协作效率

**简体中文** | [English](en/code-review.md)

状态：建议方案。适用于 PR 排队、重复争论或评审责任不清的团队。

## 问题分析

开发完成后仍可能长时间等待评审。大 PR、上下文缺失、评审集中在少数人、反馈没有优先级，都可能造成反复切换。只增加审批人数会增加等待，并不自动带来更好的判断。

## 建议做法

1. 一个 PR 聚焦一个可解释的目标，大改动先讨论设计与拆分顺序。
2. 作者写清问题、行为变化、关键决策、验证结果和剩余风险，先完成自查。
3. 标记可评审时指定合适的评审者。复杂设计可提前用 Draft PR 征求方向反馈。
4. 反馈区分“必须修改”“建议改进”“理解确认”，避免把个人偏好变成无明确理由的阻塞。
5. 对格式与静态规则优先采用自动检查，把人工时间留给正确性、兼容性、权限与维护成本。
6. 核心模块安排备份评审人，队列积压时优先处理已有 PR，再开始新任务。

## 风险分级的起点

| 类型 | 可采用的评审方式 |
| --- | --- |
| 文档和低风险调整 | 检查准确性、链接或视觉结果；按团队约定完成评审 |
| 一般功能和缺陷修复 | 一位合适的同事评审，提供必要测试证据 |
| 权限 计费 数据迁移及跨服务变更 | 领域负责人参与，确认兼容性、异常路径及恢复方案 |

审批人数和响应时间应由团队试行后确定，不作为所有仓库统一指标。代码再次发生实质变化时，确认原评审结论是否仍然有效。

## 成本与边界

拆分过细会隐藏整体影响，应通过关联 PR 或设计记录保持上下文。轮换评审不等于让不了解风险的人单独批准关键变更。暂时只有一位维护者时记录自查和验证局限，不能声称已经获得独立评审。

## 如何验证

记录从“可评审”到首次有效人工反馈的等待时间，回顾等待较久的案例及原因，同时观察合并后的缺陷与返工。等待下降但线上缺陷增加时，应调整验证方式，而不是继续追求更快批准。

下一步：选取最近一批真实 PR，判断主要瓶颈是任务大小、评审容量还是上下文缺失，再试行一项改进。
