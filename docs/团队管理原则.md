# 团队管理原则

**简体中文** | [English](en/team-principles.md)

状态：建议方案。适用于以 GitHub 协作为主的中小型研发团队，需结合实际工作方式试行。

## 用共同目标确定优先级

每个周期先明确要解决的用户或业务问题，再选择任务。需求数量超过容量时，明确取舍；新增紧急任务应同时说明哪些承诺延期。产品与研发共同评估范围、依赖和风险，不能用持续加班代替容量决策。

## 责任清楚并允许合理授权

每个任务有一位结果负责人，负责推进开发、评审、验证和交付。技术、产品、测试与发布角色分别对专业判断负责。模块负责人获得相应决策空间，重大风险明确升级，避免所有日常事项等待同一位负责人。

## 让工作状态有证据

用 Issue、PR、验证记录和发布记录支撑进展。“正在处理”应补充剩余问题和下一步；阻塞说明原因、解除责任人和检查时间。书面记录用于减少重复沟通，避免把状态维护变成额外的日报负担。

## 保持适量并行

优先完成已经开始的工作。每人先保留一个主要开发任务作为试行起点；评审和测试积压时，团队共同处理等待。这个起点不是绝对配额，线上维护、配对开发和任务性质都可能需要调整。

## 让质量责任贯穿交付

开发者提供自测证据，评审者检查关键逻辑，验收人验证目标，服务负责人观察运行情况。质量由各环节共同负责。高风险变更需要更多验证，低风险修改采用与风险相称的检查。

## 把复盘转化为系统改进

讨论事实、条件和影响，避免只归因于某个人不够认真。每次复盘优先选择少量具体改进，明确负责人和检查日期。流程过重、测试不稳定、信息不清和权限设计都可能是需要调整的系统因素。

## 支持成长并减少单点依赖

关键模块建立备份负责人，通过结对、轮换评审和运行手册传播知识。定期一对一沟通能力目标与支持需求。评价个人贡献应考虑问题解决、质量、协作、知识共享和成长，结合实际案例讨论。

## 采用方式

首次试行选择一个团队和一个交付周期，明确最需要改善的问题。记录等待、返工和协作反馈；周期结束后决定保留、调整或停止哪些约定。管理规则应有维护人，失去作用的规则可以移除。
